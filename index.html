What matters from three Claude Code videos

Distilled, checked against the official docs, and turned into one way to start. Personal notes: nothing here is adopted until I've tried it.

How to read this. The three sources are creator videos, read through auto-generated captions, so they are opinion, not evidence. Where a claim could be tested, I checked it against the Claude Code docs (Claude Code 2.1.317). Each point carries a verdict: adopt try it now, adapt useful with a change, skip not for me.

The six points that matter

Ordered by how much they should change daily work.

1 Interview first, then specify adopt

Before any spec or code, have Claude interview you one question at a time until the real goal is clear. The task ("write a report") is not the goal ("decide X").

Video 2 (layer 1) and video 3 (grill-with-docs).

Suggest: use it for new projects and new features, not for small fixes. It fits an existing "plan before building" habit by moving the thinking earlier.

2 Say how you will verify, before building adopt

Define what "done" looks like in checkable terms, then give Claude a way to run the check: tests, a build, the deployed result. The strongest idea across all three videos, and it comes with a primary source: Boris Cherny's post says a feedback loop can improve the result 2–3×.

Video 2 (layer 2). The "2–3×" figure is his claim, not a measurement of mine.

Suggest: every spec gets a required "How we verify" section. No criteria, no build.

3 Enforce what must hold with hooks, not prose adopt

CLAUDE.md is advice. The docs call it "context, not enforced configuration". A PreToolUse hook that exits with code 2, or a permission deny rule, actually blocks the action.

Video 2 (layer 3). Confirmed in the hooks and memory docs.

Suggest: a short never / ask-first / always list per project, with hooks only for the never items (secrets, production).

4 Review with a fresh context adapt

An agent reviewing code it just wrote tends to approve it. A subagent starts with an empty context and sees only what you hand it, so its review is more independent. A second model (the video's Codex plugin) goes further but is a third-party tool that the Claude Code docs don't mention.

Video 3 and video 2. Subagent behaviour confirmed in the docs.

Suggest: fresh-context review for larger changes only. Skip the second model for now.

5 Keep each task inside one bounded session adapt

Split big work into pieces that fit one session, and clear between them. The video's "smart zone ends around 140k tokens" is one person's experience, not a documented limit, so I don't copy the number.

Video 3.

Suggest: adopt the habit and measure with /context before believing any number.

6 Skills for repeated work, kept small adapt

A skill's description sits in context; its body loads only when used. A skill set to disable-model-invocation: true costs no context until you call it. Scripts inside a skill run as code, so they cost no tokens to "think". Update a skill after a mistake, but only for lessons that repeat.

Video 1 and video 3. Flags and loading behaviour confirmed in the docs.

Suggest: write a skill only after doing the task twice by hand. The videos push skills early; I'd rather let real repetition decide.

What I'm skipping

  • skip Installing the video 3 skills repo: it needs Node and a Vercel installer for 38 skills, and I want to use less than that. Read it, write my own short versions.
  • skip The "knowledge base as a moat" framing and big skill libraries, until real projects need them.
  • skip Speed claims ("10×") and "Anthropic engineers do X": quotes are secondhand clips.
  • skip The prompt "based on my recent sessions…": the docs describe no cross-session recall, so Claude would guess.

What you can really measure

No made-up numbers: these are the things Claude Code exposes.

  • /context: what is loaded now and how full the window is.
  • /usage (aliases /cost, /stats): cost and activity, with a breakdown by skill and subagent on paid plans.
  • The status line can show context-used percentage live.
  • Session transcripts in ~/.claude/projects/ contain real per-message token counts. The format is internal and may change.

Applying it: one suggestion from Claude

Start the same way every time, depending on whether the project exists.

New project

  1. Interview, no code yet.
  2. One-page spec, with "How we verify".
  3. Tiny CLAUDE.md (about 20 lines).
  4. Build the thinnest slice, check it against the spec.
  5. Note what worked in a journal.
I want to start a new project: [one-sentence idea].
Don't write code or a spec yet. Interview me one question at a time to find the real goal, who it is for, what is out of scope, and what "done" looks like. Challenge my assumptions and don't accept the first idea as decided.
When we agree, write a one-page spec with a "How we verify" section (a concrete check for each requirement) and a list of open questions. If it needs more than one session to build, propose how to split it.

Existing project

  1. Run /context in a fresh session and keep the output.
  2. Audit first, change nothing.
  3. Fix the top findings one by one.
  4. Re-run /context to see the effect.
Audit how this project is set up for Claude Code. Read only: change nothing.
Look at: the size of CLAUDE.md files and what loads at startup (here is my /context output: [paste]); rules repeated in more than one place; rules that are only advice but should be enforced by a hook or a deny rule; whether specs say how work is verified; tasks I repeat that could become a skill.
Give the top 5 findings ranked by impact, each with the file, the problem, and a suggested fix. Don't suggest tools or structure beyond that.
Rule of thumb. Add a tool, a skill, a hook or a document only when its absence has already cost me something. Interview and verification apply to almost everything. The rest earns its place.
